PIPES BAKERY - TESTING STRATEGY AND TEST INVENTORY

1. Objective

The testing strategy of this project verifies the application by layers and by risk:

- Fast unit tests for business rules, frontend utilities, HTTP service wrappers and page/component behavior in isolation.
- Integration tests for backend persistence, Spring wiring, serialization and real controller-service-repository flows.
- A backend smoke test to confirm the Spring Boot application context starts correctly.
- A frontend component-flow test layer to validate the admin area, checkout validations and request orchestration without needing a browser E2E stack.

This combination is appropriate because the project contains:

- Non-trivial checkout and order-management rules.
- JWT authentication and role-based access control.
- An admin panel with create/edit/delete/update actions.
- REST contracts where a small regression can break the frontend immediately.
- A React SPA where routing, request orchestration and validation messaging are critical to the user experience.

2. Testing technologies and why they were chosen

2.1. Backend technologies

- JUnit 5
  Purpose: base test framework for the Java backend.
  Justification: standard, stable and already integrated with Spring Boot and Maven Surefire.

- Mockito
  Purpose: isolate service and controller unit tests through mocks and stubs.
  Justification: ideal for verifying business rules and repository/service interactions without hitting infrastructure.

- Spring Boot Test
  Purpose: bootstraps real application slices or the full Spring context.
  Justification: necessary to validate security configuration, serialization, dependency wiring and end-to-end backend flows.

- MockMvc
  Purpose: exercises REST endpoints without deploying a real servlet container.
  Justification: the most efficient way to validate HTTP contracts, status codes and JSON payloads in controller tests.

- H2/test profile infrastructure already present in the backend
  Purpose: run repository and integration tests with real persistence.
  Justification: gives confidence in JPA mappings and transactional flows while keeping tests fast and deterministic.

2.2. Frontend technologies

- Vitest
  Purpose: frontend test runner.
  Justification: it integrates naturally with Vite, is fast, supports ESM without extra ceremony, and is the most coherent choice for a Vite-based React project. Choosing Jest here would add more configuration and less native compatibility.

- React Testing Library
  Purpose: render components/pages and assert user-visible behavior.
  Justification: it encourages testing from the user's perspective instead of testing implementation details, which is especially important for pages like AdminLoginPage, CheckoutPage, OrdersAdmin and ProductsAdmin.

- @testing-library/jest-dom
  Purpose: richer DOM assertions such as toBeInTheDocument and toBeDisabled.
  Justification: improves readability and reduces noisy low-level assertions.

- @testing-library/user-event
  Purpose: simulate richer user interactions when needed.
  Justification: keeps the suite future-proof for realistic interactions, even though many current tests are already covered with fireEvent.

- jsdom
  Purpose: browser-like DOM environment for Vitest.
  Justification: necessary to execute React component and page tests in Node while preserving DOM APIs like document, localStorage and form behavior.

2.3. Why no E2E framework was added in this iteration

- Tools such as Playwright or Cypress are valuable, but they would introduce a heavier infrastructure and slower pipelines.
- At the current project maturity, the highest value comes from stabilizing unit and component-flow tests first.
- The newly added suite already validates the most fragile frontend flows without requiring a running browser or backend.

4. Coverage achieved

With the current suite, the project is explicitly covered in these areas:

- Backend application startup.
- Backend CRUD for addresses, clients and products.
- Backend order retrieval, publicId usage and status patching.
- Backend checkout rules:
  - non-empty cart
  - valid address
  - Bogota city normalization
  - Colombia country restriction
  - zip code format 11xxxx
- Password hashing and admin-only login token issuance.
- Admin login brute-force protection:
  - 5 failed attempts create a temporary lock
  - existing locks reject login
  - Redis-backed per-minute rate windows reject excessive login traffic
  - successful login clears failed-attempt state
- JWT generation, extraction and validation.
- Cookie-based admin authentication without localStorage token persistence.
- Frontend CSRF behavior:
  - fetch CSRF token for authenticated admin sessions
  - attach CSRF token to unsafe admin requests
  - avoid attaching CSRF token to public cart requests
- Frontend cart recovery behavior when a stored cart no longer exists.
- Frontend lazy cart creation on first add-to-cart instead of on anonymous page entry.
- Frontend suppression of expected cart lookup 404 console logging.
- Frontend admin login flow and logout flow.
- Frontend admin section switching.
- Frontend product admin ingredient-list behavior.
- Frontend order admin loading and status update flow.
- Frontend checkout page validation, payload construction and success redirect.
- Frontend presentation of backend-provided totals in checkout.
- Backend checkout conversion preserves frozen cart prices when creating order items.

5. Strategy behind the suite

The suite follows a pragmatic testing pyramid:

- Broad base of unit tests
  Used for backend services, frontend utilities and HTTP wrappers.
  Benefit: very fast feedback and precise failure localization.

- Middle layer of integration tests
  Used mainly in the backend to validate Spring, JPA, JSON serialization and transactional flows.
  Benefit: high confidence that real infrastructure and domain logic collaborate correctly.

- Frontend component-flow tests
  Used for pages and admin components where the main risk is user interaction, routing and request orchestration.
  Benefit: strong UX validation without the cost of full browser E2E infrastructure.

This balance is especially suitable here because:

- The backend carries substantial business logic and persistence concerns.
- The frontend carries orchestration, validation and admin workflow complexity.
- The project benefits more from fast, maintainable regression protection than from a small number of slow browser tests.

6. Why the new security and frontend tests were necessary

These frontend and security tests were added because the project had an important validation gap:

- There was no automated verification for the React application.
- Recent changes introduced admin authentication, protected admin navigation, product management, order management and checkout refinements.
- Recent hardening introduced CSRF protection for unsafe admin requests and rate limiting for admin login.
- Checkout now has an explicit frozen-price policy that must not regress before real payments are added.
- Several frontend flows depend on exact request shapes and navigation behavior; those regressions are easy to miss manually.
- The cart recovery and order status patching flows had already shown that frontend/backend contract mismatches can break production behavior.

The new suite is necessary to guarantee:

- stable API contract usage from the client
- stable route and layout behavior
- stable cookie-based admin authentication and logout behavior
- stable CSRF token retrieval and header injection for admin mutations
- stable login brute-force protection based on IP and email
- stable frozen-price order creation
- stable list-based ingredient editing in products
- stable order status updates using PATCH
- stable checkout validations and order completion flow
